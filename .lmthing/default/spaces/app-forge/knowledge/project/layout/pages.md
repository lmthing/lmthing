## `views/` — a page is a spec, not source code

A page is a **view spec**: `views/<route>.view.json`, a plain object `{ route, title?, layout?, sections }` rendered at runtime by the shared `ViewRenderer`. There is NO hand-written `pages/*.tsx` medium — that format and its per-project build were removed; a spec is never compiled, only fetched and rendered. `views:write` is the ONE UI-authoring capability and it earns exactly the spec writers: `writeProjectView` (a page), `writeProjectViewLayout` (`views/<prefix>/_layout.view.json`, frames every route beneath it), `writeProjectViewComponent` (`components/<Name>.view.json`) and `writeProjectViewShell` (`shell.view.json` — nav, brand, assistant dock).

The ROUTE is the authoring form: no leading slash, no extension, kebab-case segments, `[param]` for a dynamic one, `index` for a directory root — `recipes/[id]`, never `/recipes/:id`. One route vocabulary everywhere: the page's own route, a nav target and a `{ navigate }` action are compared as strings, so validate the route before writing (`checkPagePath`). A route with a `[param]` is a drill-in reached by `rowAction`/`navigate`, never a nav destination.

Sections: a closed union of eight kinds — `list`, `detail`, `create`, `stats`, `markdown`, `chat`, `toolbar`, `timeline`. A `create` section declares NO fields; they derive from the mutation's Input schema (`@x-options` on a foreign-key Input property feeds its select). There is no `custom` kind and no React escape hatch: a surface the vocabulary cannot express is REPORTED, never forced into the nearest kind. Bindings are paths from exactly eight roots (`$`, `$.field`, `$props.x`, `$route.param`, `$data.<sectionId>.path`, `$result.field`, `$form.field`, `$client.timezone`) — no expressions, ever; computation lives in the endpoint's Output or a named policy. One section, one endpoint, and the endpoint's Output must satisfy that section's bindings.

Grounded: `org/docs/format/project/pages/view-spec.md`, `org/docs/app/routes.md`.
